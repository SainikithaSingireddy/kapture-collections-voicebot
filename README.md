# Kapture Collections Voicebot

## Overview

This project is a prototype AI-powered collections voicebot built for the Kapture Finance take-home assignment.

The voicebot, **Maya**, handles an overdue-loan conversation with a customer in a polite and compliant manner. The prototype is built using **Vapi** for the voice agent and a **Node.js/Express mock backend** deployed on Render for business tools and state management.

### Example Customer

* **Customer:** Rahul Sharma
* **Account ID:** ACC-88392
* **Loan:** Personal Loan
* **Overdue EMI:** ₹8,499
* **Days overdue:** 12

---

## Architecture

```text
Customer
   ↓
Vapi Voice Assistant
   ├── Speech-to-Text
   ├── LLM / Conversation Orchestrator
   └── Text-to-Speech
          ↓
      Vapi Tools
          ↓
   Render / Node.js / Express
          ↓
   Mock Customer + Session State
```

The backend exposes a single `/webhook` endpoint. Vapi sends the selected tool name and parameters to this endpoint, and the backend returns a structured JSON response.

---

## Conversation Flow

The assistant follows a state-controlled collections flow:

```text
GREETING
   ↓
AUTHENTICATION
   ↓
AUTHENTICATED
   ↓
NEGOTIATION
   ├── Promise to Pay → PTP_COLLECTED → Payment Link → End
   ├── Already Paid → Disposition → End
   ├── Do Not Call → Disposition → End
   ├── Dispute → Escalate to Agent
   └── Hardship → Escalate to Agent
```

A key design decision is that authentication is enforced by the backend state, not only by the prompt.

The assistant must successfully call `verify_customer` before revealing the customer's loan or overdue amount.

## Tools

The Vapi assistant uses the following backend tools:

### 1. verify_customer

Verifies the customer's identity before any financial information is disclosed.

**Inputs:**

* `account_id`
* `verification_code`

**Output:**

* `verified`
* `customer_name`
* `state`
* `message`

---

### 2. get_account_details

Retrieves the customer's overdue account information after successful authentication.

**Output:**

* `customer_name`
* `amount`
* `due_date`
* `days_overdue`

---

### 3. start_negotiation

Moves an authenticated customer into the payment negotiation state.

---

### 4. log_promise_to_pay

Records the customer's payment commitment.

**Example information:**

* Promise-to-pay date
* Amount

The backend changes the session state to `PTP_COLLECTED`.

---

### 5. send_payment_link

Simulates sending a payment link to the customer's registered mobile number.

**Input:**

* `channel`

The prototype supports SMS as the simulated channel.

---

### 6. mark_disposition

Records the final outcome of the conversation.

Supported outcomes include:

* `ALREADY_PAID`
* `DO_NOT_CALL`
* `WRONG_PERSON`

---

### 7. escalate_to_agent

Escalates cases that require human intervention.

Examples include:

* `DISPUTE`
* `HARDSHIP_REQUEST`

A mock ticket ID is generated by the backend.

---

### 8. end_call

Completes the call after the appropriate business outcome has been recorded.

## Authentication and Compliance

The most important guardrail is:

> **The bot must never disclose debt information before successful customer verification.**

Before authentication, Maya does not reveal:

* Loan details
* EMI amount
* Overdue status
* Debt information

If the wrong person answers, the bot does not disclose financial information and can record a `WRONG_PERSON` disposition.

The bot is also designed to:

* Identify the company and purpose appropriately.
* Use respectful, non-threatening language.
* Handle do-not-call requests.
* Handle already-paid claims.
* Escalate disputes and financial hardship.
* Avoid making unsupported claims.
* Use backend tool results for business actions.

## What Broke and How I Debugged It

During testing, the successful Promise-to-Pay flow exposed a state-machine issue.

After `log_promise_to_pay` completed successfully, the backend changed the session state to:

```text
PTP_COLLECTED
```

However, the `send_payment_link` function originally allowed only:

```text
AUTHENTICATED
NEGOTIATION
```

Therefore, the payment-link API returned an error because the conversation was already in `PTP_COLLECTED`.

The issue was identified from the Vapi call logs.

I updated the backend so that `send_payment_link` also accepts:

```text
PTP_COLLECTED
```

I also updated disposition handling so that edge cases such as `ALREADY_PAID`, `DO_NOT_CALL`, and `WRONG_PERSON` can be recorded appropriately.

This demonstrated the importance of enforcing conversation state in the backend instead of relying only on the LLM prompt.

## Limitations

This is an assignment prototype and not a production collections system.

Current limitations include:

* Customer data is mocked.
* Session state is stored in memory.
* Payment-link delivery is simulated.
* No real banking or loan-management system is connected.
* No real SMS provider is connected.
* The backend is intended for demonstration rather than production use.
